# Host adapter: T3 Code

Maps the host contract in `core/MODEL.md` to T3's MCP tools (server `t3-code`; Claude sees them
as `mcp__t3-code__<name>`).

| Contract | T3 tool | Notes |
| --- | --- | --- |
| `launch` | `t3_thread_launch` | `projectId` = the node's `host_project`. `workspaceStrategy: {"type":"root"}` runs in the node folder; `{"type":"worktree",…}` gives an isolated copy of a git home. |
| `send` | `t3_thread_send` | |
| `wait` | `t3_thread_wait` | |
| `read` | `t3_thread_read` | |
| `list` | `t3_thread_list` | Gives each thread's `updatedAt`, used by the freshness check. |
| `delegate` | `delegate_task` | |
| `schedule` | `schedule_task` | Record it in `schedules.md` (`brain schedule add`) and bind the returned id on this machine (`brain schedule bind`). |
| `pending` | `t3_pending_request_list` | Answer with `t3_pending_request_respond`; `t3_pending_request_read` gives the whole question. |
| `watch` | `watch_pull_request` | Also `link_pull_request`, so the thread lists its pull requests. |

`hosts/t3.env` gives `brain` the thread link format.

## A node in T3

T3 IDs belong to one machine's T3, so `brain set` keeps them in `.brain/local.json`, not in
`node.md` (axiom 23). `brain show <node>` reads them back.

- **One T3 project per node folder** (`t3_project_create`, `workspaceRoot` = the node folder):
  `brain set <node> host_project=<id>`. Look in `t3_project_list` first; it may exist.
- **A sealed node** whose home is a git repo also needs a T3 project for the home, so workers
  can run in worktrees there: `brain set <node> home_project=<id>`.
- **The coordinator thread**: `t3_thread_launch` in the node's project, titled
  `<title> · coordinator`. Pin it with `t3_thread_organize`, and record it with
  `brain set <node> coordinator=<threadId>`.
- **Before launching workers**: group by concern and gather shared facts once. Generate each
  brief with `brain brief --why-separate "<reason>" --context-file <shared findings>`;
  declare common source paths in the contract's `## Inputs`. Overlap advice in `brain jobs`
  and `brain due` means merge related jobs or share context; it does not block independent work.
  Shared context clears that pair from due; jobs retains a softer shared-context line.
- **Work in an external home**: `brain wt add <node> <branch>` makes the worktree (in the node's
  workbench, with its setup and port), then `t3_thread_launch` in the `home_project` with
  `workspaceStrategy: {"type":"existing_worktree", "worktreePath": <path>, "branch": <branch>}`.
  The operator's own checkout is never touched. (T3's own `{"type":"worktree"}` also works, but
  puts the worktree in T3's folder, without the node's setup or a port.)
- **Hand-back**: a thread started with `t3_thread_launch` notifies no one when it ends; only
  `delegate_task` children do. So every worker brief (`brain brief`) tells the worker to
  `t3_thread_send` only start, done, blocked or question to its coordinator.
- **Times**: T3 gives `updatedAt` and run times in UTC (`…Z`). `brain show` gives a node's
  status time in UTC as well, for the freshness check.
- **Review by the other runtime**: `delegate_task` with `target` set to a provider instance of
  the reviewer runtime (`orchestrator_capabilities` lists them) and the brief from `brain review`.
  `delegate_task` runs in the caller's checkout, so put the worktree path in the brief, or use
  `t3_thread_launch` in the worktree as above when the reviewer must run there.
- **Pull requests**: after a worker opens one, `watch_pull_request` wakes the coordinator on
  reviews, CI results and conflicts; `brain sync` covers everything else others do.
  With `brain set <node> merge=pr`, the coordinator explicitly runs `brain sync <node>`,
  then `brain ready <node> --branch <branch>`, then `gh pr merge <number> --merge
  --match-head-commit <verified-head>` (or the home's required squash strategy).
  Readiness compares cached `origin/HEAD`, and reports stale local default-branch lag without
  touching the operator checkout. A moved base returns to the worker for rebase and handback.
  Sync again after merging: external default-branch integrations enter the ledger once by hash.
  The merge setting documents the mode; no host merge is automatic.
- **Models**: provider instance and model IDs come from `orchestrator_capabilities`.
  `t3_project_create` ignores `defaultModelSelection`, so set it afterwards with
  `t3_project_update`.
  After a delegated launch, save the declared `modelSelection` JSON object and
  the returned receipt (or its `structuredContent`) to private files. Before
  accepting the route as checked, run `brain launch-check <node>
  --selection-file <selection.json> --receipt-file <receipt.json>`. The adapter
  must supply the actual returned `providerInstanceId`, `model` and explicit
  `options`, not the request's echoed `target`. Object and descriptor-array
  options compare equally; duplicate or missing values are unknown. A mismatch
  or unknown result exits nonzero. A match checks only returned metadata:
  host execution and provider behavior remain outside this validator.
- **Usage-limit recovery**: `.brain/local.json` has `fallback`, a plain ordered list of host
  provider instance ids, for example `["claudeAgent", "codex"]`. Set it with
  `brain set root fallback=claudeAgent,codex`; it is per machine and never committed.
  On a job thread's usage-limit failure, read its terminal state and stop any old run before
  launching a replacement. Pick the next eligible subscription with `brain usage` and brief
  routing; `fallback` breaks ties. Use `orchestrator_capabilities` for its runtime and model.
  Regenerate the same task's `brain brief <node> --branch <branch>` (set `--runtime` to the replacement runtime),
  then `t3_thread_launch` in the **existing worktree**, with that resume brief and selected
  provider instance. Keep the original task and constraints; read and continue existing commits,
  ready packet and ledger state. Record `brain jobs <node> --branch <branch> --switch
  "<old> -> <new>: usage limit"` before generating the brief; update the Active work thread
  after launching it. If all remaining instances
  are exhausted or absent, report the blocker. This is host recovery, not a second job.
- **Links for the operator**: `[<title>](t3-thread://v1/<threadId>)`.
- **Usage per thread** (checked 2026-10-20): T3's thread records carry times, provider and model,
  no token counts. `brain` counts a job's tokens from the runtimes' own transcripts on this
  machine: a thread launched in the job's worktree, a `delegate_task` reviewer given the review
  brief (it runs in the coordinator's checkout and is found by the `brain-job:` line its brief
  carries), and any session the worker's `brain handback` recorded (Claude Code and Codex tell
  their shells their session id). If a host reports usage per thread, record it with
  `brain jobs <node> --branch <branch> --usage-file <json>`; it wins over the transcripts.

## Hand-back in T3 (tested 2026-10-19)

`brain machine wake-setup <node>` prints a provisioning plan from the current local
coordinator binding. Hand the plan to that exact coordinator thread and run its
`schedule_task` payload there: `schedule: {"type":"webhook"}` and
`bindToCurrentThread: true` bind the calling thread. A root caller cannot create
this binding on another thread's behalf. Regenerate the plan after rebinding the
coordinator. The command performs no host call and prints no existing capability.
After host creation, bind the returned URL locally with the printed `brain set`
command. If the host returns no `webhookUrl`, enable T3 Connect remote access first.
Keep the capability URL private; a printed plan does not establish provisioning.

Home workers now finish with `brain handback --state done|blocked|question --summary '<one-line result>' --lessons ...`:
their one file carries state, proposed lessons and readiness. The coordinator's interval tick
runs `brain due`; a host message may link the record but is optional. A question also appends
to the node inbox and requires `--question '<one-line choice>'`; blocked human needs use `--need-human "<need>"`. Repeating the same need
is deduplicated. A runtime question tool is still visible through `t3_pending_request_list`,
so the tick checks both file due items and host pending requests. Do not rely on a question
left only in the worker's idle thread. Small briefs use a one-line hand-back to the coordinator.

## Settle a closed job's threads

Brain records closure and reminds; it never calls the host API. After `wt rm`, `wt prune`,
or an import study's `jobs --close`, follow the printed checklist. Before closing, mark the
Active work row `merged`, `abandoned`, or `closed` as appropriate and retain its worker thread. `brain due <node>` and the
live state report the number of closed jobs whose threads are not yet recorded settled.
`brain due root` includes child settlement counts. Old closed ledger rows count too: inspect the backlog.

1. Read `brain jobs <node> --branch <branch>`: the ledger must have Ended and an explicit
   terminal outcome (merged, abandoned, studied or closed). Never settle any coordinator or
   any thread belonging to an open job, even if idle. If the branch has been reused, distinguish
   jobs by their `brain-job: <key>` marker; leave ambiguous ownership unsettled.
2. Find the worker thread in the node's **Active work**, including its closed rows. Use
   `t3_thread_list` with `includeSubagents=true`, paginate to exhaustion in both the node's
   `host_project` and `home_project`, and include both settled and unsettled threads. Follow
   `parentThreadId` recursively to find delegated/sub-agent threads.
   Find reviewers with `t3_thread_search` for the exact `brain-job: <key>` line printed by jobs;
   include their descendants too. Search matches are candidates: read their first prompt and
   metadata to confirm ownership; a quoted marker alone is not proof. Search is bounded,
   project-scoped and active-only, with no exhaustive-result guarantee: an empty search never
   proves no threads exist. Cross-check paginated lists and first prompts in both projects;
   if complete coverage cannot be established, leave unsettled. Do not settle the parent
   coordinator or unrelated threads. A missing old worker reference alone does not prevent
   settlement attestation: use the complete-project sweep below for legacy jobs without markers.
3. Check fresh host state and `t3_pending_request_list` for **each** candidate, including nested
   threads. Never settle a running or waiting thread or one with pending requests. Unknown
   state is unsafe. Preparing, queued and starting runs are also unsafe. Resolve work through the coordinator first; recheck immediately before
   `t3_thread_organize` with `action="settle"` and one explicit `threadId` per call. If anything remains active, waiting, ambiguous,
   or fails to settle, leave the job unsettled and handle it on a later tick.
4. Only after all its threads are confirmed settled (or exhaustive project lists show no
   attributable unsettled thread remains), save a fresh structured export and run
   `brain jobs <node> --branch <branch> --settled --attestation-file <export.json>`. This records the
   coordinator's host attestation, not an independent CLI check. Do not mark partial cleanup.
   For a reused branch, include the printed `--job-key <key>` to select its exact ledger row.
   The timestamp is idempotent and belongs to that ledger job, not later jobs on the branch.

The export is version 1 JSON. Supply `node`, a fresh ISO `observed_at` (at most five
minutes old), `project_ids` covering every bound host/home project, and
`coverage: {"project": true, "nested": true, "complete": true}`. A single `project_id`
is accepted when it covers all bound projects. `jobs` contains exactly the selected
job keys, each as `{"job_key": "<key>", "threads": [...]}`. Every thread entry needs
its singular `threadId`, matching `job_key`, terminal `state` (`completed`, `failed`,
`interrupted`, `cancelled` or `rolled_back`), `settled: true`, and
`pending_requests: []`. Include reviewers and nested descendants. An empty thread
list is an explicit exhaustive observation, never an inference from a missing binding.
Core validates the supplied evidence against recorded ownership; it does not independently
query the host or prove that the coordinator's observations were complete.

### Sweep a legacy backlog

Older jobs may have neither a marker nor an Active work row. List exhaustion is the proof;
search only finds candidates and cannot prove absence. The coordinator can clear this backlog:

1. List **every unsettled thread** (`settled=false`, `includeSubagents=true`) in both the node's
   `host_project` and `home_project`, paginating each to exhaustion. Read the ledger, Active work,
   coordinator bindings, thread metadata and pending requests; include nested threads. An
   unavailable project or an incomplete listing is not a completed sweep.
2. Protect every coordinator and all threads belonging to open jobs or active work. Never
   settle a running, waiting, preparing, queued or starting thread, or one with pending requests.
   Recheck immediately before settling. Leave doubtful threads alone. After complete enumeration
   rules out the protected groups, an otherwise unattributed idle thread with no pending requests
   counts as closed work even when no old job marker or worker reference survives. Settle safely
   done closed-work threads with `t3_thread_organize action="settle" threadId="<one exact ID>"`, one call per thread.
3. Re-enumerate to exhaustion after cleanup. A closed job with **no attributable unsettled
   thread left after a full list** may be recorded settled, even if it had no surviving marker
   or worker reference. This does not require proving that the job never had host threads.
   Known protected threads may remain. If any retained doubtful or unsafe thread might still
   belong to closed work, defer the bulk attestation until that ambiguity or activity clears.
4. Record the completed sweep with `brain jobs <node> --settled --all-closed --attestation-file <export.json>`. The fresh export must cover every selected job and both project lists. This stamps all
   already-closed, unsettled rows together, preserves existing stamps and never stamps open rows.
   It refuses the entire update if a branch it would stamp has any open ledger job; no rows
   change on refusal. Later jobs on a reused branch start unsettled. Use per-job `--settled`
   for new jobs or when only individual jobs' cleanup is complete.

## Hooks in T3 (tested 2026-10-18)

T3 runs both runtimes with their project hooks: a Claude thread and a Codex thread started in a
node folder both ran `brain hook stop`, kept going when the notes were behind, and finished with
the right answer for their role. For Codex, `brain hook approve` must have run first on that
machine (the machine-setup skill does it).

## Missing worker workspace

A thread whose workspace folder has disappeared can fail to receive messages without the
sender noticing. Before `brain wt prune` or train worktree cleanup, inspect the listed
`worker:<key>` bindings and Active work references. Message each finished worker while its
workspace still exists: tell it the job is done and request any final hand-back. Confirm it
has stopped, reconcile pending requests, then settle it with `t3_thread_organize` before
pruning. Threads already settled need no message. The CLI only lists host steps; it never
calls the host. `--dry-run` lists references without fetching, pruning Git metadata, sending
messages or settling threads; its listing includes the host plan to complete before actual
removal. A real prune removes the folder in that same command: if the message was missed,
do not send it afterwards. Inspect and safely settle through the host only, then use a fresh
thread in a fresh worktree for follow-on work. The same guidance applies to `brain wt rm`.

Message helpers warn when a target's recorded job workspace is gone or no longer registered.
An unregistered workspace may live on another machine; confirm it through the host before
sending. Import-study threads run in the node and do not need a worktree. Rotation omits
already settled historical jobs from its warning list. Stop messaging threads whose workspace
is confirmed gone. For follow-on work, create a fresh worktree with `brain wt add`
and launch a fresh thread there. For recovery of an unfinished job whose worktree still
exists, re-launch with `t3_thread_launch` and
`workspaceStrategy: {"type":"existing_worktree","worktreePath":"<job-worktree>","branch":"<job-branch>"}`
on the job's own worktree, using its resume brief and existing state. Do not recreate the
folder at a new path. If the job's worktree is gone, recover it at its recorded location
before launching; never borrow a merged job's folder or switch its branch.

## Known gaps

- T3 settles idle threads after 3 days. That's harmless, because state lives in files
  (axiom 16).
- Codex in worktrees (tested 2026-10-16 and 2026-10-18, codex-cli 0.162.1): a git worktree
  inherits its main checkout's trust **and** hook approvals. Codex reads the hook list from the
  main checkout's `.codex/hooks.json` and runs the hook scripts that are in the worktree. An
  untrusted plain copy of the repo loads neither.

## Coordinator self-wake

Use `schedule_task` with an interval, for example `schedule: {"type":"interval","everyMs":3600000}`,
targeting the existing coordinator thread (not a new thread per tick). Discover the host's
current target fields from its tool schema. Record the schedule with `brain schedule add`,
and bind its returned host id with `brain schedule bind` on one machine only. A scheduled task
re-launches its bound thread on the provider it was created under; changing a thread's provider
does not migrate the schedule. Recreate the schedule on the intended provider when switching.
The tick prompt:

> Role: coordinator of node `<id>`. Run `brain due <id>` and check
> `t3_pending_request_list` for this coordinator and each worker thread in Active work.
> Inspect current bound workers for terminal run failures and atomically export the local
> failure records described below; no completed hand-back does not prove a worker is running.
> Run `brain watch --once` after exporting so a new failure is routed promptly.
> If this is root, enumerate every descendant node by starting at `brain show root`, then
> recursively following each `children` list with `brain show <child>`, and call `t3_pending_request_list` with each child's coordinator thread id.
> Cover every child coordinator by default, including nested nodes and those without open jobs;
> an absent coordinator binding is a setup gap to record, never evidence of no questions.
> The CLI captures supported runtime questions when their stop hook runs, but cannot see live
> host pending requests. `brain due root` covers child settlement counts too; route their unsettled-thread
> counts to their coordinators. Settle closed jobs by the checklist above, never open jobs,
> coordinators, running/waiting threads or threads with pending requests. If due work and all
> host checks are empty, end at once, saying nothing and changing no
> files. If only `blocked-overdue` items remain and no host request needs action, run
> `brain inbox <id> --new`, route only new escalations, then end without refreshing or
> committing unchanged status. Otherwise act on the due work, record the merge or next step in your own files,
> update judgement sections, then `brain status <id> --refresh` and commit. Report only
> `brain inbox <id> --new` or new work worth showing; never relist old needs-you items.
> For a root daily brief, check child freshness and send only behind signals to their
> coordinators. Each coordinator runs and marks its own sync; root never runs child sync.
> The root reports to the human; other coordinators handle only their subtree and route
> unresolved needs to their parent. Their independent reporter state never consumes root's queue.

The hourly interval is a safety net for host-only requests and adapter failure.
The minute, non-AI watcher and PR watches provide actionable wakes for coordinators and root. `brain due` uses files and local git only: no host inference, network fetch,
or squash-merge claim. A locally merged branch with an open ledger needs reconciliation;
legacy jobs without hand-back signals are unknown, not assumed finished. The generated
facts label open ledger jobs honestly: the CLI cannot prove a runtime is still running.

## Question wake transport

From each coordinator's existing thread, create a webhook task with `schedule_task`:
`schedule: {"type":"webhook"}`, `bindToCurrentThread: true`, and `prompt` equal to that
coordinator's normal tick above. Omit `projectId` to bind this thread's project. Keep the
returned task id in the machine's schedule bindings. Store the returned `webhookUrl` with
`brain set <node> wake=<webhookUrl>`; never commit or report the capability URL. If no URL
is returned, enable T3 Connect remote access, then inspect the task again. Never substitute
a local webhook path for a public URL. Creating real tasks requires the operator's consent.

`brain wake <node> "<reason>"` wakes that node's coordinator, or root if it has no coordinator.
`brain set root wake_default=<command-or-URL>` supplies a machine default; `wake=` overrides
it per coordinator. These values stay in `.brain/local.json`. A URL receives a POST with
`{"event":"brain-wake"}`; a configured shell command receives the same JSON on stdin, runs
at the instance root and must wake the intended coordinator. No transcript, question, node
name or reason is sent. The bound tick reads the durable inbox; it needs no request placeholders.

The Stop hook and question/blocked hand-backs enqueue wakes locally. New inbox episodes get distinct reasons; repeats while unanswered are suppressed. Explicit
reasons are deduplicated for 24 hours by digest under `.brain/wake/`, with one delivery attempt per two minutes per answering node.
A detached Python worker delivers immediately or waits out the rate window, coalescing queued
reasons into one tick. Commands have a ten-second timeout; HTTP requests use the same socket
timeout and refuse redirects. Caller execution never waits for delivery. Failures retain the
pending reasons; the worker retries for up to ten minutes and `brain due` restarts pending
workers after an interruption. The inbox line remains the record even when no transport is set.

Keep one hourly interval per coordinator, including root, for host-only pending requests.
Replace the former fifteen-minute coordinator and five-minute root AI ticks only with operator
consent after configuring and testing the watcher transport. Without a working transport,
retain the existing recovery schedule until setup is complete. `brain due` and the live view label captured or
hand-back questions older than ten minutes as `overdue-question`, routed to root; `brain due`
requests a root wake once for each overdue inbox line. Set `question_minutes=<minutes>` on a
node to change the threshold. A coordinator removes answered inbox lines so they no longer
escalate. Wake delivery alone does not prove a question was answered. Hosts that do not emit
Stop while a question is pending still require live host pending checks on the fallback tick.

## Local train ejections

After `brain train <node>`, read the node's `job-trains/*.json` queue/ejection records.
For each ejected job, use `t3_thread_send` on its existing Active work worker thread with
the conflict file list or failing verify log path, batch id and original contract. The CLI
does not call the host or overwrite the worker's hand-back. A new worker hand-back permits
retry. Keep the train's printed push command for the separately authorized release.

## Coordinator rotation

On a `rotate` due item run `brain rotate <node>` and read its handover. Before stopping the old
thread, inventory its host schedules, webhook wake tasks and pending requests, including open
workers. Launch a fresh coordinator in the node's project with the file handover (not the old
transcript), update `brain set <node> coordinator=<new host thread id>`, then append the new
runtime session id with `brain set <node> coordinator_sessions=<new id>` (the normal `=`
form retains history and moves that id last). These are separate IDs:
use `CODEX_THREAD_ID` / `CLAUDE_CODE_SESSION_ID` from the new coordinator shell for accounting.
Recreate/rebind schedules and wake tasks to the new thread, preserving prompts, intervals and
provider routing, and update `brain schedule bind` and `wake=` locally. Capability URLs must
never enter the handover. Reconcile every pending ask before telling the old thread to stop;
confirm it stopped and has no pending requests before settling through the host. The CLI
cannot enumerate unrecorded host tasks and never invokes T3 itself.

## Worker messages

Workers use `t3_thread_send` to their coordinator only for start, done, blocked or question.
Format with `brain msg <node> <kind> "<one line>"` (branch/report added when known), or use handback.
Shared-commit coordination goes directly to the peer thread named in the brief; ask for its id once if missing.
The brief states the protocol and `brain msg` rejects other kinds; host delivery stays with the worker.
Use `brain brief --peer <thread>` to name the direct shared-commit peer in each worker brief.

## File watcher and failed worker runs

`brain watch --once` computes actionable due identities and screened excerpts in machine-local
`.brain/watch.json`. The machine-care minute unit (`brain machine sample`) samples first, then
runs the watcher after releasing the sampler lock. An existing unit picks up this behavior
on core upgrade; installing a missing unit requires operator consent. Do not add a second AI or sampler timer. Stale-status refresh alone
never wakes. Hand-back readiness display changes do not make another item. Seen identities
survive removal from due. New sets enqueue through `brain wake`'s transport and two-minute
rate limit; failed sends retain their pending queue and inbox. Supported Stop-hook questions
and question/blocked hand-backs enqueue directly. The watcher checks their stable pending/sent
receipts and retries a missed enqueue; a recorded direct wake never creates a second request.
Overdue questions wake root without copying their text. An unreadable watcher state fails
closed: restore it rather than deleting dedup history. No host API, network fetch or model
is used by the watcher; only the configured wake transport may communicate outward.

A host integration or active coordinator must record terminal failed worker runs locally.
The watcher cannot discover a failure the adapter has not written; the hourly safety-net tick
must inspect bound worker status as well as pending requests. This release does not implement
a host exporter. Without a separately configured exporter, detection waits until that hourly
tick (up to one hour, plus the watcher's next minute); it is not an immediate failure wake.
Bind or replace each current worker under the instance lock with
`brain set <node> worker:<brain-job-key>=<thread-id>`; an empty value removes the binding.
These bindings stay machine-local; do not hand-edit local.json. Atomically write `.brain/worker-runs.json` with this shape (made-up data):

```json
{"version":1,"runs":[{"node":"sample","job_key":"example-job-key","thread":"example-thread",
 "run":"example-run","status":"failed","runtime":"codex","error":"model at capacity"}]}
```

Use the actual terminal run identity, not its changing update time. Record failures from
provider errors, usage limits and model capacity. Keep only a short error category; never
write host transcripts or credentials. The watcher validates the worker binding against an
open ledger job, writes one screened inbox line and wakes once per failed run. Closed or
unbound runs do nothing. Processed failures remain acknowledged after their inbox is cleared.
The router disables automatic other-runtime retries, including at-capacity failures and
legacy jobs without a class. The watcher records the failure notice and wake, without a
runtime switch, `Capacity retry` marker or retry command. Builders stay on Codex; only an
explicit runtime choice at the stop line may select an eligible alternative. The coordinator
confirms the old run is terminal before any authorized relaunch through T3 in the existing
worktree, then updates the worker binding. The watcher never launches a model. A later failed
run still wakes for help.

Malformed host failure files are skipped with one warning per invalid episode; ordinary due
items still wake. Invalid class or routing configuration never suppresses that record's failure
notice. Invalid watcher acknowledgement state remains fail-closed; the sampler prints a short
diagnostic and `brain due root` reports `watcher state invalid` until it is restored.


### Typed coordinator notifications

Use the native `brain notify` route for coordinator-to-root communication. Its
landing, park and FYI records never call a wake transport. Questions carry typed
options, recommendation, deadline and default. Direct host sends and host-owned
schedule/completion notifications bypass this API; the core cannot intercept
those channels or infer a host's queue state. Configure those host channels to
use the same route rather than claiming a universal interception guarantee.


## Addressed machine-local inventory

`brain host-instance remember desk --machine sample-machine --adapter t3 --file bindings.json`
stores an addressed descriptor in private local state. The JSON file maps node
IDs to `host_project`, `home_project` and/or `coordinator` bindings. Inventory
entries never contain wake capabilities and never enter shared notes.
`brain host-instance route desk --node sample` selects an existing descriptor;
`brain host-instance plan --node sample` reports local versus remote execution
without printing its host IDs. A remote route requires execution on that machine;
the local native bridge never dispatches to it. Local descriptors must match
existing bindings; selection does not rebind them.

`brain host provision sample --require-no-auto-settle` refuses before setup
because this adapter has no supported auto-settlement control. Pinning remains
available and does not imply that policy changed.
