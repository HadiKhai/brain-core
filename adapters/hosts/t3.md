# Host adapter: T3 Code

Maps the host contract in `core/MODEL.md` to T3's MCP tools (server `t3-code`; Claude sees them
as `mcp__t3-code__<name>`).

| Contract | T3 tool | Notes |
| --- | --- | --- |
| `launch` | `t3_thread_launch` | `projectId` = the node's `host_project`. `workspaceStrategy: {"type":"root"}` runs in the node folder; `{"type":"worktree",…}` gives an isolated copy of a git home. |
| `send` | `t3_thread_send` | |
| `wait` | `t3_thread_wait` | |
| `read` | `t3_thread_read` | |
| `list` | `t3_thread_list` | Gives each thread's `updatedAt`, used by the freshness check. |
| `delegate` | `delegate_task` | |
| `schedule` | `schedule_task` | Record it in `schedules.md` (`brain schedule add`) and bind the returned id on this machine (`brain schedule bind`). |
| `pending` | `t3_pending_request_list` | Answer with `t3_pending_request_respond`; `t3_pending_request_read` gives the whole question. |
| `watch` | `watch_pull_request` | Also `link_pull_request`, so the thread lists its pull requests. |

`hosts/t3.env` gives `brain` the thread link format.

## A node in T3

T3 IDs belong to one machine's T3, so `brain set` keeps them in `.brain/local.json`, not in
`node.md` (axiom 23). `brain show <node>` reads them back.

- **One T3 project per node folder** (`t3_project_create`, `workspaceRoot` = the node folder):
  `brain set <node> host_project=<id>`. Look in `t3_project_list` first; it may exist.
- **A sealed node** whose home is a git repo also needs a T3 project for the home, so workers
  can run in worktrees there: `brain set <node> home_project=<id>`.
- **The coordinator thread**: `t3_thread_launch` in the node's project, titled
  `<title> · coordinator`. Pin it with `t3_thread_organize`, and record it with
  `brain set <node> coordinator=<threadId>`.
- **Work in an external home**: `brain wt add <node> <branch>` makes the worktree (in the node's
  workbench, with its setup and port), then `t3_thread_launch` in the `home_project` with
  `workspaceStrategy: {"type":"existing_worktree", "worktreePath": <path>, "branch": <branch>}`.
  The operator's own checkout is never touched. (T3's own `{"type":"worktree"}` also works, but
  puts the worktree in T3's folder, without the node's setup or a port.)
- **Hand-back**: a thread started with `t3_thread_launch` notifies no one when it ends; only
  `delegate_task` children do. So every worker brief (`brain brief`) tells the worker to
  `t3_thread_send` its coordinator when it finishes, fails, gets blocked or has a question.
- **Times**: T3 gives `updatedAt` and run times in UTC (`…Z`). `brain show` gives a node's
  status time in UTC as well, for the freshness check.
- **Review by the other runtime**: `delegate_task` with `target` set to a provider instance of
  the reviewer runtime (`orchestrator_capabilities` lists them) and the brief from `brain review`.
  `delegate_task` runs in the caller's checkout, so put the worktree path in the brief, or use
  `t3_thread_launch` in the worktree as above when the reviewer must run there.
- **Pull requests**: after a worker opens one, `watch_pull_request` wakes the coordinator on
  reviews, CI results and conflicts; `brain sync` covers everything else others do.
- **Models**: provider instance and model IDs come from `orchestrator_capabilities`.
  `t3_project_create` ignores `defaultModelSelection`, so set it afterwards with
  `t3_project_update`.
- **Links for the operator**: `[<title>](t3-thread://v1/<threadId>)`.

## Hooks in T3 (tested 2026-10-18)

T3 runs both runtimes with their project hooks: a Claude thread and a Codex thread started in a
node folder both ran `brain hook stop`, kept going when the notes were behind, and finished with
the right answer for their role. For Codex, `brain hook approve` must have run first on that
machine (the machine-setup skill does it).

## Known gaps

- T3 settles idle threads after 3 days. That's harmless, because state lives in files
  (axiom 16).
- Codex in worktrees (tested 2026-10-16 and 2026-10-18, codex-cli 0.162.1): a git worktree
  inherits its main checkout's trust **and** hook approvals. Codex reads the hook list from the
  main checkout's `.codex/hooks.json` and runs the hook scripts that are in the worktree. An
  untrusted plain copy of the repo loads neither.
