# Host adapter: T3 Code

Maps the host contract in `core/MODEL.md` to T3's MCP tools (server `t3-code`; Claude sees them
as `mcp__t3-code__<name>`).

| Contract | T3 tool | Notes |
| --- | --- | --- |
| `launch` | `t3_thread_launch` | `projectId` = the node's `host_project`. `workspaceStrategy: {"type":"root"}` runs in the node folder; `{"type":"worktree",…}` gives an isolated copy of a git home. |
| `send` | `t3_thread_send` | |
| `wait` | `t3_thread_wait` | |
| `read` | `t3_thread_read` | |
| `list` | `t3_thread_list` | Gives each thread's `updatedAt`, used by the freshness check. |
| `delegate` | `delegate_task` | |
| `schedule` | `schedule_task` | |

## A node in T3

- **One T3 project per node folder** (`t3_project_create`, `workspaceRoot` = the node folder).
  Store its id in `node.md` with `brain set <node> host_project=<id>`.
- **A sealed node** whose home is a git repo also needs a T3 project for the home, so workers
  can run in worktrees there. Record it as `home_project`.
- **The coordinator thread**: `t3_thread_launch` in the node's project, titled
  `<title> · coordinator`. Pin it with `t3_thread_organize`, and record it with
  `brain set <node> coordinator=<threadId>`.
- **Models**: provider instance and model IDs come from `orchestrator_capabilities`.
  `t3_project_create` ignores `defaultModelSelection`, so set it afterwards with
  `t3_project_update`.
- **Links for the operator**: `[<title>](t3-thread://v1/<threadId>)`.

## Known gaps

- T3 settles idle threads after 3 days. That's harmless, because state lives in files
  (axiom 16).
- Codex trusts each project folder separately. A new worktree folder may not load the home's
  own Codex config. Test this before relying on it.
