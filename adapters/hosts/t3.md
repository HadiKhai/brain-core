# Host adapter: T3 Code

Maps the host contract in `core/MODEL.md` to T3's MCP tools (server `t3-code`; Claude sees them
as `mcp__t3-code__<name>`).

| Contract | T3 tool | Notes |
| --- | --- | --- |
| `launch` | `t3_thread_launch` | `projectId` = the node's `host_project`. `workspaceStrategy: {"type":"root"}` runs in the node folder; `{"type":"worktree",…}` gives an isolated copy of a git home. |
| `send` | `t3_thread_send` | |
| `wait` | `t3_thread_wait` | |
| `read` | `t3_thread_read` | |
| `list` | `t3_thread_list` | Gives each thread's `updatedAt`, used by the freshness check. |
| `delegate` | `delegate_task` | |
| `schedule` | `schedule_task` | Record it in `schedules.md` (`brain schedule add`) and bind the returned id on this machine (`brain schedule bind`). |
| `pending` | `t3_pending_request_list` | Answer with `t3_pending_request_respond`; `t3_pending_request_read` gives the whole question. |
| `watch` | `watch_pull_request` | Also `link_pull_request`, so the thread lists its pull requests. |

`hosts/t3.env` gives `brain` the thread link format.

## A node in T3

T3 IDs belong to one machine's T3, so `brain set` keeps them in `.brain/local.json`, not in
`node.md` (axiom 23). `brain show <node>` reads them back.

- **One T3 project per node folder** (`t3_project_create`, `workspaceRoot` = the node folder):
  `brain set <node> host_project=<id>`. Look in `t3_project_list` first; it may exist.
- **A sealed node** whose home is a git repo also needs a T3 project for the home, so workers
  can run in worktrees there: `brain set <node> home_project=<id>`.
- **The coordinator thread**: `t3_thread_launch` in the node's project, titled
  `<title> · coordinator`. Pin it with `t3_thread_organize`, and record it with
  `brain set <node> coordinator=<threadId>`.
- **Before launching workers**: group by concern and gather shared facts once. Generate each
  brief with `brain brief --why-separate "<reason>" --context-file <shared findings>`;
  declare common source paths in the contract's `## Inputs`. Overlap advice in `brain jobs`
  and `brain due` means merge related jobs or share context; it does not block independent work.
  Shared context clears that pair from due; jobs retains a softer shared-context line.
- **Work in an external home**: `brain wt add <node> <branch>` makes the worktree (in the node's
  workbench, with its setup and port), then `t3_thread_launch` in the `home_project` with
  `workspaceStrategy: {"type":"existing_worktree", "worktreePath": <path>, "branch": <branch>}`.
  The operator's own checkout is never touched. (T3's own `{"type":"worktree"}` also works, but
  puts the worktree in T3's folder, without the node's setup or a port.)
- **Hand-back**: a thread started with `t3_thread_launch` notifies no one when it ends; only
  `delegate_task` children do. So every worker brief (`brain brief`) tells the worker to
  `t3_thread_send` its coordinator when it finishes, fails, gets blocked or has a question.
- **Times**: T3 gives `updatedAt` and run times in UTC (`…Z`). `brain show` gives a node's
  status time in UTC as well, for the freshness check.
- **Review by the other runtime**: `delegate_task` with `target` set to a provider instance of
  the reviewer runtime (`orchestrator_capabilities` lists them) and the brief from `brain review`.
  `delegate_task` runs in the caller's checkout, so put the worktree path in the brief, or use
  `t3_thread_launch` in the worktree as above when the reviewer must run there.
- **Pull requests**: after a worker opens one, `watch_pull_request` wakes the coordinator on
  reviews, CI results and conflicts; `brain sync` covers everything else others do.
  With `brain set <node> merge=pr`, the coordinator explicitly runs `brain sync <node>`,
  then `brain ready <node> --branch <branch>`, then `gh pr merge <number> --merge
  --match-head-commit <verified-head>` (or the home's required squash strategy).
  Readiness compares cached `origin/HEAD`, and reports stale local default-branch lag without
  touching the operator checkout. A moved base returns to the worker for rebase and handback.
  Sync again after merging: external default-branch integrations enter the ledger once by hash.
  The merge setting documents the mode; no host merge is automatic.
- **Models**: provider instance and model IDs come from `orchestrator_capabilities`.
  `t3_project_create` ignores `defaultModelSelection`, so set it afterwards with
  `t3_project_update`.
- **Usage-limit recovery**: `.brain/local.json` has `fallback`, a plain ordered list of host
  provider instance ids, for example `["claudeAgent", "codex"]`. Set it with
  `brain set root fallback=claudeAgent,codex`; it is per machine and never committed.
  On a job thread's usage-limit failure, read its terminal state and stop any old run before
  launching a replacement. Pick the next eligible subscription with `brain usage` and brief
  routing; `fallback` breaks ties. Use `orchestrator_capabilities` for its runtime and model.
  Regenerate the same task's `brain brief <node> --branch <branch>` (set `--runtime` to the replacement runtime),
  then `t3_thread_launch` in the **existing worktree**, with that resume brief and selected
  provider instance. Keep the original task and constraints; read and continue existing commits,
  ready packet and ledger state. Record `brain jobs <node> --branch <branch> --switch
  "<old> -> <new>: usage limit"` before generating the brief; update the Active work thread
  after launching it. If all remaining instances
  are exhausted or absent, report the blocker. This is host recovery, not a second job.
- **Links for the operator**: `[<title>](t3-thread://v1/<threadId>)`.
- **Usage per thread** (checked 2026-10-20): T3's thread records carry times, provider and model,
  no token counts. `brain` counts a job's tokens from the runtimes' own transcripts on this
  machine: a thread launched in the job's worktree, a `delegate_task` reviewer given the review
  brief (it runs in the coordinator's checkout and is found by the `brain-job:` line its brief
  carries), and any session the worker's `brain handback` recorded (Claude Code and Codex tell
  their shells their session id). If a host reports usage per thread, record it with
  `brain jobs <node> --branch <branch> --usage-file <json>`; it wins over the transcripts.

## Hand-back in T3 (tested 2026-10-19)

Home workers now finish with `brain handback --state done|blocked|question --lessons ...`:
their one file carries state, proposed lessons and readiness. The coordinator's interval tick
runs `brain due`; a host message may link the record but is optional. A question also appends
to the node inbox; blocked human needs use `--need-human "<need>"`. Repeating the same need
is deduplicated. A runtime question tool is still visible through `t3_pending_request_list`,
so the tick checks both file due items and host pending requests. Do not rely on a question
left only in the worker's idle thread. Small briefs use a one-line hand-back to the coordinator.

## Settle a closed job's threads

Brain records closure and reminds; it never calls the host API. After `wt rm`, `wt prune`,
or an import study's `jobs --close`, follow the printed checklist. Before closing, mark the
Active work row `merged`, `abandoned`, or `closed` as appropriate and retain its worker thread. `brain due <node>` and the
live state report the number of closed jobs whose threads are not yet recorded settled.
`brain due root` includes child settlement counts. Old closed ledger rows count too: inspect the backlog.

1. Read `brain jobs <node> --branch <branch>`: the ledger must have Ended and an explicit
   terminal outcome (merged, abandoned, studied or closed). Never settle any coordinator or
   any thread belonging to an open job, even if idle. If the branch has been reused, distinguish
   jobs by their `brain-job: <key>` marker; leave ambiguous ownership unsettled.
2. Find the worker thread in the node's **Active work**, including its closed rows. Use
   `t3_thread_list` with `includeSubagents=true`, paginate to exhaustion in both the node's
   `host_project` and `home_project`, and include both settled and unsettled threads. Follow
   `parentThreadId` recursively to find delegated/sub-agent threads.
   Find reviewers with `t3_thread_search` for the exact `brain-job: <key>` line printed by jobs;
   include their descendants too. Search matches are candidates: read their first prompt and
   metadata to confirm ownership; a quoted marker alone is not proof. Search is bounded,
   project-scoped and active-only, with no exhaustive-result guarantee: an empty search never
   proves no threads exist. Cross-check paginated lists and first prompts in both projects;
   if complete coverage cannot be established, leave unsettled. Do not settle the parent
   coordinator or unrelated threads. A missing old worker reference alone does not prevent
   settlement attestation: use the complete-project sweep below for legacy jobs without markers.
3. Check fresh host state and `t3_pending_request_list` for **each** candidate, including nested
   threads. Never settle a running or waiting thread or one with pending requests. Unknown
   state is unsafe. Preparing, queued and starting runs are also unsafe. Resolve work through the coordinator first; recheck immediately before
   `t3_thread_organize` with `action="settle"`. If anything remains active, waiting, ambiguous,
   or fails to settle, leave the job unsettled and handle it on a later tick.
4. Only after all its threads are confirmed settled (or exhaustive project lists show no
   attributable unsettled thread remains), run `brain jobs <node> --branch <branch> --settled`. This records the
   coordinator's host attestation, not an independent CLI check. Do not mark partial cleanup.
   For a reused branch, include the printed `--job-key <key>` to select its exact ledger row.
   The timestamp is idempotent and belongs to that ledger job, not later jobs on the branch.

### Sweep a legacy backlog

Older jobs may have neither a marker nor an Active work row. List exhaustion is the proof;
search only finds candidates and cannot prove absence. The coordinator can clear this backlog:

1. List **every unsettled thread** (`settled=false`, `includeSubagents=true`) in both the node's
   `host_project` and `home_project`, paginating each to exhaustion. Read the ledger, Active work,
   coordinator bindings, thread metadata and pending requests; include nested threads. An
   unavailable project or an incomplete listing is not a completed sweep.
2. Protect every coordinator and all threads belonging to open jobs or active work. Never
   settle a running, waiting, preparing, queued or starting thread, or one with pending requests.
   Recheck immediately before settling. Leave doubtful threads alone. After complete enumeration
   rules out the protected groups, an otherwise unattributed idle thread with no pending requests
   counts as closed work even when no old job marker or worker reference survives. Settle safely
   done closed-work threads with `t3_thread_organize action="settle"`.
3. Re-enumerate to exhaustion after cleanup. A closed job with **no attributable unsettled
   thread left after a full list** may be recorded settled, even if it had no surviving marker
   or worker reference. This does not require proving that the job never had host threads.
   Known protected threads may remain. If any retained doubtful or unsafe thread might still
   belong to closed work, defer the bulk attestation until that ambiguity or activity clears.
4. Record the completed sweep with `brain jobs <node> --settled --all-closed`. This stamps all
   already-closed, unsettled rows together, preserves existing stamps and never stamps open rows.
   It refuses the entire update if a branch it would stamp has any open ledger job; no rows
   change on refusal. Later jobs on a reused branch start unsettled. Use per-job `--settled`
   for new jobs or when only individual jobs' cleanup is complete.

## Hooks in T3 (tested 2026-10-18)

T3 runs both runtimes with their project hooks: a Claude thread and a Codex thread started in a
node folder both ran `brain hook stop`, kept going when the notes were behind, and finished with
the right answer for their role. For Codex, `brain hook approve` must have run first on that
machine (the machine-setup skill does it).

## Known gaps

- T3 settles idle threads after 3 days. That's harmless, because state lives in files
  (axiom 16).
- Codex in worktrees (tested 2026-10-16 and 2026-10-18, codex-cli 0.162.1): a git worktree
  inherits its main checkout's trust **and** hook approvals. Codex reads the hook list from the
  main checkout's `.codex/hooks.json` and runs the hook scripts that are in the worktree. An
  untrusted plain copy of the repo loads neither.

## Coordinator self-wake

Use `schedule_task` with an interval, for example `schedule: {"type":"interval","everyMs":900000}`,
targeting the existing coordinator thread (not a new thread per tick). Discover the host's
current target fields from its tool schema. Record the schedule with `brain schedule add`,
and bind its returned host id with `brain schedule bind` on one machine only. A scheduled task
re-launches its bound thread on the provider it was created under; changing a thread's provider
does not migrate the schedule. Recreate the schedule on the intended provider when switching.
The tick prompt:

> Role: coordinator of node `<id>`. Run `brain due <id>` and check
> `t3_pending_request_list` for this coordinator and each worker thread in Active work.
> If this is root, enumerate every descendant node by starting at `brain show root`, then
> recursively following each `children` list with `brain show <child>`, and call `t3_pending_request_list` with each child's coordinator thread id.
> Cover every child coordinator by default, including nested nodes and those without open jobs;
> an absent coordinator binding is a setup gap to record, never evidence of no questions.
> The CLI captures supported runtime questions when their stop hook runs, but cannot see live
> host pending requests. `brain due root` covers child settlement counts too; route their unsettled-thread
> counts to their coordinators. Settle closed jobs by the checklist above, never open jobs,
> coordinators, running/waiting threads or threads with pending requests. If due work and all
> host checks are empty, end at once, saying nothing and changing no
> files. If only `blocked-overdue` items remain and no host request needs action, run
> `brain inbox <id> --new`, route only new escalations, then end without refreshing or
> committing unchanged status. Otherwise act on the due work, record the merge or next step in your own files,
> update judgement sections, then `brain status <id> --refresh` and commit. Report only
> `brain inbox <id> --new` or new work worth showing; never relist old needs-you items.
> For a root daily brief, check child freshness and send only behind signals to their
> coordinators. Each coordinator runs and marks its own sync; root never runs child sync.
> The root reports to the human; other coordinators handle only their subtree and route
> unresolved needs to their parent. Their independent reporter state never consumes root's queue.

An interval tick replaces root or human nudges; hand-back sends and PR watches still give
faster wakes. `brain due` uses files and local git only: no host inference, network fetch,
or squash-merge claim. A locally merged branch with an open ledger needs reconciliation;
legacy jobs without hand-back signals are unknown, not assumed finished. The generated
facts label open ledger jobs honestly: the CLI cannot prove a runtime is still running.
